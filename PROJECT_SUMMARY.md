# Approximately Up — Flight Computer Project

Carried over from the earlier "gyro-line" chat (claude.ai), 2026-10-01. The goal is an automated flight computer for a ship in *Approximately Up* (a Steam spaceship-building sandbox) that handles hover, obstacle avoidance, level flight, autopilot cruise and planet scanning.

## Repository

GitHub: https://github.com/austinsc/au-sim (public, created 2026-10-02).
- The simulator is published on GitHub Pages at https://austinsc.github.io/au-sim/, served from the `gh-pages` branch as `index.html`, a copy of `circuit-simulator.html`. The workflow `.github/workflows/pages.yml` refreshes that copy whenever `circuit-simulator.html` changes on main. It can also be run by hand from the Actions tab.
- Raw game extracts (prefab dumps, meshes) are left out by `.gitignore`; the scripts in `tools/bp` rebuild them from a local install.

## Confirmed from the game files (2026-10-01)

Source: `C:\Program Files (x86)\Steam\steamapps\common\Approximately Up\ApproximatelyUp_Data\StreamingAssets\Localization.csv`, which holds the game's own part descriptions and in-game manual. Class names come from `il2cpp_data/Metadata/global-metadata.dat`. This is a Unity IL2CPP build. The logic itself is compiled native code, so these files give the documented behaviour, not the implementation.

- **Tick rate.** The manual's "Component Delay" page says the game runs at a fixed rate of **60 ticks per second**. This confirms the earlier inference.
- **Every component adds one tick of delay, including Data Routers.** The manual's example: 10 Data Routers between a Lever and a Datameter means the signal takes 11 ticks to arrive. The one exception is a chain of connected Frame Quarter With Ports, which acts as a single 1-tick delay.
  - **Every feedback loop is legal,** because every block delays. The engine now models this (2026-10-01).
- **No NOR gate exists.** The only gates are `LogicGateAnd`, `LogicGateNot`, `LogicGateOr` and `LogicGateXor`. The wiki's NOR (and the NOR-based clock) must be built as NOT(OR).
- **Fuse Box** is a power part, not a logic part. It disconnects batteries when power exceeds a set P/s limit (basic power cables carry 150 P/s) and has to be switched back on by hand.
- **Whiteboard** is decorative: "Used for drawing or writing on it."
- **Wireless Transmitter** links all devices set to the same channel, within 2000 m. Several receivers can share a channel, but only one transmitter may send on it.
- **Differentiator** (confirmed from the game code, 2026-10-02): every `interval` ticks it outputs the input minus the input at its previous update, and holds that value in between. It does not divide. The knob has 12 positions: 1, 2, 3, 4, 5, 6, 10, 12, 15, 20, 30 or 60 ticks.
- **Condition:** an unconnected True input defaults to **1**, and an unconnected False input defaults to **0**.
  - The in-game mode order is 0 Equal, 1 Not Equal, 2 Less, **3 Less Equal, 4 Greater**, 5 Greater Equal.
  - aupbuilder's JSON uses 3 `>` and 4 `≤`. Treat aupbuilder's `op` as its own encoding, not the game's.
- **Gyro-Line** outputs pitch tilt in degrees on port 0 and roll tilt in degrees on port 1, and needs power. A "Display Range" setting exists. The `÷ −30` convention is not in the game text.
- **Further game parts, added to the engine 2026-10-01:**
  - **Math:** Asin, Acos, Atan, **Atan2**, Sinh/Cosh/Tanh, Exp and Log
  - **Logic Value:** 1 if the input is ≥ 0.5
  - **Fader:** input × knob value from 0 to 1. An unconnected input defaults to 1.
  - **Initializer:** outputs 0 until N ticks after entering Fly Mode, because block chains output junk while initializing.
  - **Datameter:** a display with a pass-through output
- **Name mapping:**
  - The 7-input `sum` is the game's **Addition Array**.
  - `sign_splitter` is the game's "Sign Splitter" (internal name `JoystickSplitter`). Port 1 is negative-as-positive and port 2 is positive.
  - `data_redirector_3` is `SignalRouter3`, with the selector on port D taking 0..1.
- **Sensors relevant to the open subsystem gaps:**
  - **Distance Meter:** reaches 1000 m. This is the obstacle-avoidance sensor.
  - **Long Range Distance Meter:** a single ray with unlimited range.
  - **Space Scanner:** scans a cone from 1° to 50°, set by a 0..1 input, and outputs the distance to the nearest body. This is the planet-scan sensor.
    - Confirmed from the game code (`SCTick_SpaceScanner`):
      - The cone is `50 − 49 × input` degrees, so input 0 = 50° and 1 = 1°.
      - A body counts once any of its disk is inside the cone: the angle to its centre minus its angular radius ≤ cone/2.
      - The output is the surface distance (centre distance − radius) of the nearest such body. When the cone is empty it is **1e20**, the data clamp, not 0.
  - **Axis Rotometer:** angular velocity (deg/s) about its own local +y axis (game code). Mounted upright it reads yaw; on its side, pitch.
  - **Gravitymeter:** outputs gravity in m/s². This provides planet_hop's gravity input directly.
  - **Other useful sensors:** Inclinometer (degrees between the part's down direction and gravity), Axis Rotometer (deg/s about its mounted axis) and Massmeter.
- **Accelerometer** outputs acceleration in m/s². Game code (`SCTick_Accelerometer`): it is the magnitude of the ship's change of velocity, |Δv| × 60, smoothed by `out += (new − out) × 0.08` a tick, so gravity is included (free fall reads g, resting on the ground reads 0) and the mounting direction does not matter. The BPS manual pairs an Accelerometer, a Velocity Meter and a Long Range Distance Meter.
- **Velocity Meter** (game code, `SCTick_VelocityMeter`): `_modeButton` 0 (Overall) outputs |v|, 1 (Directional) outputs v · (the part's +z), signed; both smoothed by `out += (new − out) × 0.1535` a tick. It needs a clear view ahead.
- **Thruster response** (game code, `SCTick_ValueAccelerator`): a thruster's output moves toward its input by at most 1 / `acceleration_time` per second (a slew limit, not a lag): Small/Medium Electric 0.25 / 0.7 s, Electric Flat 0.2 s, maneuvering 0.1–0.35 s, RCS Thruster 0.04 s, but **Small Fuel 10 s and Medium Fuel 20 s**. Fuel engines cannot follow an autopilot's throttle; drive only electrics from a fast loop.
- **Maneuvering Thrusters** ("all the power is used for rotation", `force_type` 1): small 30 kN, medium 100 kN, large 370 kN, bidirectional 80 kN; they turn the ship by position × force about the centre of mass and do not push it. Throttle input 0..1 and power (5 / 17 / 50 / 15 P/s). Each is a rod pushing along its length, mounted by its long side; the exhaust end's heat zone runs 3 / 5 / 7 m.
- **RCS** (`SC_GimbalController` + `SC_GimbalThruster`): "RCS Controller for 6 RCS Thrusters". The thrusters are wireless 1 × 1 × 0.5-quarter plates (10 kN, also rotation only) with a **single-use 700 P battery** (5 P/s while firing, ~140 s each). Mode k = `_channel` (2k + 1)/12: 0/1 yaw left/right, 2/3 pitch down/up, 4/5 roll left/right (corpus torque analysis, signs tentative).
- **Small Solid Fuel Thruster ignition** (game code, `SCTick_Thruster_SolidFuel`):
  - Until it ignites, the thruster requests its ignition power: 200 P/s (`solid_fuel_ignition_power`; the port text reads "Requires {0} P/s to ignite").
  - Each tick an ignition progress changes by 1/60, clamped to 0..1. It rises unless the part's electric status byte is 2, the value that means not powered.
  - At 1.0 it ignites, after **60 consecutive powered ticks (1 s)**. Its power demand then drops to 0, and it cannot be stopped.
  - Every unpowered tick undoes one powered tick, so an interrupted ignition takes longer.
  - Whether a partly supplied network counts as powered is unconfirmed.
- **Wireless Transmitter:** one sender per channel ("the red light means multiple transmitters are broadcasting on the same channel, which is not allowed"); range 2,000 m; no power. Its single port has no joint area on top of the part.
- **Space GPS** outputs distance, longitude (−180..180) and latitude (−90..90), and needs at least 60% clear space around it.
- **Blueprints** (`.bp`) are binary with hashed type IDs and are not decoded yet. `.bpmeta` files are small JSON (`_name`, `_folder`, `_version`).

**Not recovered** (they existed only in the old chat): `three_state_cycle.json`, `travel_to_target.json` and the Playwright browser tests. `raster_sweep.json` was rebuilt from scratch, and `test_engine.js` was replaced by `test/engine.test.js`.

## Fan-wiki facts (approximatelyupgame.online) — where these conflict with the section above, the game files win

- **Cables** need a solid surface. An unsupported run of roughly 5–8 tiles snaps. Press `H` in build mode to highlight bad wires.
- **Frame ports** only connect to other frame ports.
- **Port colors:** red = power, yellow = data-in, blue = data-out.
- **Confirmed logic parts:** Constant Number, Remapper, Delay Block, Memory, AND/OR/NOR gates, Accumulator, Data Router, Wireless Transmitter, BPS braking, Fuse Box and Whiteboard. The wiki never says what Fuse Box and Whiteboard do.
- **Data Hub** routes 1 of 5 inputs to its output, chosen by a channel selector.
- **No clock part exists.** The community builds one from a NOR gate and a Data Router wired into a self-loop.
- **Gyro-Line** outputs signed pitch/roll in degrees and needs power. It feeds the auto-level loop through `÷ −30`.
- **Trajectory curvature** outputs degrees, but the trig functions take radians.
- **Tick rate of 60/sec is inferred, not confirmed.** The evidence is the Delay Block's 1–60 tick cap and the community's "1/60" differentiator convention.

## aupbuilder.arkadhub.com (third-party circuit tool)

The JSON schema is a top-level object with no wrapper:
```
{ instances: [{id, type_id, parameters, position, color, mirrored}],
  edges: [{from_instance, from_port, to_instance, to_port, color}],
  groups, max_per_column, max_rows, max_columns }
```

Confirmed type_ids and ports:

- **Sources:** `constant`, `toggle`, `slider` (`value` param → `out`)
- **Routers:** `data_router_2` (`in` → `a`,`b`) and `data_router_4` (`in` → `a`..`d`). One output can drive only one input, so routers are required for fan-out.
- **Logic:** `not`, `and`, `or`, `xor` (`a`,`b` → `out`); `simple_threshold` (`in`,`threshold` → `out`)
- **Condition:** `condition` (`a`,`b`,`true`,`false`,`op` → `out`). The `op` codes are 0 `=`, 1 `≠`, 2 `<`, 3 `>`, 4 `≤`, 5 `≥`.
- **Arithmetic:** `subtractor`, `multiplier`, `divider` (not `"divide"`) and `mod`. **`adder` was pattern-matched and never verified.**
- **Stateful:** `accumulator` (`in`,`reset`,`mode`; adds `in` each tick), `memory` (`value`,`set`,`mode`), `delay` (`in`,`ticks`) and `differentiator` (`in`,`interval`,`simulate`)

**Limitation:** aupbuilder rejects every cycle, including one that passes through a stateful block. That rules out self-resetting sawtooth and raster patterns, which is why the custom simulator was built.

## Custom simulator (engine.js)

- **Schema:** it uses the same JSON schema as aupbuilder.
- **Type ids:**
  - Type ids for parts aupbuilder lacks (`exp`, `log`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `logic_value`, `fader`, `initializer` and `datameter`) were chosen by me and are unverified against aupbuilder.
  - `nor` was removed because the game has no NOR part.
- **Tick model (the game's rule):**
  - Every block is a 1-tick stage. Each tick, every block computes from the outputs all blocks held at the end of the previous tick, then all new outputs commit together.
  - Declaration order doesn't matter, and every loop is legal.
  - A block N stages downstream of a source sees a change N ticks later. For example, a lever through 10 routers takes 11 ticks.
- **Stateful blocks** fold their input in on the same tick they output:
  - The Accumulator outputs the new total.
  - Memory outputs the newly latched value.
  - The Differentiator outputs `x − x_at_last_update`, refreshed every `interval` ticks.
- **Delay** total latency is exactly `ticks` (1–60), its own tick included. Confirmed from the game code (`DELAY_ADDS_TO_COMPONENT_TICK = false`).
- **Logic gates** treat any non-zero input as true. **Unconfirmed:** the game may use the >= 0.5 rule.
- **Not modelled:**
  - Wireless Tx, which pairs by channel rather than by wire
  - Frame Quarter With Ports chains, which take one tick for the whole chain
  - Fuse Box and Whiteboard, which are not logic parts
- **Every in-game part with data or power ports** (173 types, added 2026-10-01) is listed in `GAME_PARTS` in engine.js. Port lists follow the game's own port order (`SC_<Part>_PortN`), and a test checks them against `part_text.json`.
  - **Port kinds:** data, power (undirected, one cable per port), video and plasma. Kinds can only connect to their own kind.
  - **Controls and sensors** output their reading as a block setting. Sensors that need power read 0 when unpowered.
  - **Displays, lights, thrusters, gates and other actuators** show a status line instead of an output (for example `50%`, `no power`, `DETONATED`).
  - **Wireless Transmitter:** the game's single bidirectional port is split into `tx` (wired in = transmit) and `rx`. Two transmitters on one channel conflict.
- **Power model** (each tick, before the blocks compute):
  - Power ports are joined into circuits by cables, Power Routers, two-port Solar Panels, closed Fuse Boxes and Power Blockers whose `block` input is below 0.5.
  - **Powered** means the circuit has a source and its generation covers demand, or its batteries hold the shortfall for this tick (P/s ÷ 60 Units per tick). Surplus recharges rechargeable batteries only.
  - **Demand:** constant for most parts; proportional to |input| for electric thrusters, fans, Ballast, Floodlight and the Plasma Generator; only while the input is non-zero for fuel thrusters; only while the input is ≥ 0.5 for the Rimcore Turbopump and Lava Pumping Tank; only on the tick the input changes for gates, valves and the Extendable Damper.
  - **Fuse Box** trips and stays off when its circuit draws more than `limit_ps` (default 150, the basic cable rating). Switch it back on by hand.
  - **Not in the game files:** every P/s figure, generator output and battery capacity sits in stripped asset data that UnityPy can't decode. They are block settings (`power_ps`, `gen_ps`, `capacity`, `charge`) to copy from each part's in-game tooltip.
- **UI:** the page shows a tick counter (game time = tick / 60). Play still steps at 10 ticks/s, so it runs slower than real time.
- **Zoom** (2026-10-02):
  - **Controls:** −/+, Fit and 1:1 in the canvas corner. Ctrl/⌘ + wheel or a trackpad pinch zooms at the cursor. The range is 10–200%.
  - **Implementation:** a CSS transform on `#canvas`, with `#canvasSizer` giving the scroll area the scaled size. All pointer and port coordinates are divided by `zoom`.
  - **Panning:** pressing on empty canvas or the space around it only pans. Native image and text dragging is blocked over the canvas and the palette.
  - **Other:** new blocks from the palette appear in the current view, and Tidy layout ends with Fit.
- **Selection and clipboard** (2026-10-02):
  - **Selecting:** Shift/Ctrl/⌘-click toggles a block in the selection, Shift-drag on empty canvas box-selects (add Ctrl to extend), Ctrl+A selects everything, Esc deselects and a plain click on empty canvas deselects. Dragging any selected block moves the group, and Delete removes it.
  - **Clipboard:** Ctrl+C/X/V copies the selected blocks plus every wire with both ends inside the group. Pasting gives each block a fresh id and re-links the wires, while wires leading out of the group are dropped.
  - **System clipboard:** the group is written as JSON tagged `au-sim-blocks`, so it pastes into another simulator tab. If the browser sends no paste event, the in-page copy is used.
  - **Paste position:** a paste lands where you last clicked on empty canvas since copying, otherwise 40 px below-right of the originals, stepping on each repeat.
- **Header:** fits on one line. Buttons have short labels with tooltips, and the status message truncates (hover to read it all); it only wraps below 760 px.
- **Tidy layout** (button, 2026-10-02) runs a layered layout.
  - **Columns:** blocks are arranged by data flow, with feedback loops reversed just for that step. Sources sit next to their first consumer, and power-only parts share their consumer's column.
  - **Wire lanes:** every wire that crosses a column gets a reserved lane in that column. Wires run in the gaps between columns, so none pass behind a block.
  - **Ordering:** blocks within each column are ordered and aligned with their neighbours.
  - **Routes:** routes aren't saved in the exported JSON. They are dropped when the wiring changes, and per wire when you drag a block.
  - **Measured result:** on the planet_hop demo, wires behind blocks went from 19 to 0 and overlapping blocks from 2 to 0, in 75 ms. Four random circuits with loops and power cables also gave 0.

## Circuits

1. **raster_sweep.json** is a yaw/pitch raster sweep for planet scanning.
   - **Loop-free design** (redesigned for the tick model):
     - One accumulator sums `yaw_step × enable` and never resets.
     - `yaw = total mod range`.
     - `row = floor(total / range)`.
     - `pitch_cmd = (row mod rows) × pitch_step − span/2`, where `rows = floor(span / pitch_step) + 1`.
     - `yaw_cmd = (yaw + offset) mod 360`.
   - **Why loop-free:** a self-resetting loop would overshoot by the loop's latency, which is several ticks.
   - **Timing:** the yaw path is padded with 2 Data Routers so yaw and pitch both come out 6 ticks after the accumulator, and pitch steps on exactly the tick yaw wraps.
   - **aupbuilder:** with no cycle, it should also load there, if aupbuilder has `round`, which is unverified.
   - **Defaults:** step 2°, range 360, pitch step 20 and span 120 give 7 rows from −60° to +60°. That is 180 ticks per row and 1,260 ticks per frame (21 s).
   - **Pitch restart:** pitch jumps from +60 back to −60. It does not sweep back and forth.
   - **Enable off** freezes both axes.
   - **Precision:** the accumulator total grows without bound. With float32 in the game, non-integer steps lose precision only after hours of continuous sweeping.
   - **Start-up:** for the first few ticks after Fly Mode starts, the outputs read 0 while the paths fill.
   - **Blueprint:** installed 2026-10-02 as "raster sweep (6 fq, black, I/O row)" in the in-game folder "au-sim gen"
     (`e06d9658-a1e5-4ec9-bca9-7d27bfa8abc2.bp`). It is 12×8×4, with all 8 I/O in one two-row bundle on −z.
     It replaces "raster sweep (labels)" (`b55a4378`), which used the old colours.
2. **raster_sweep_v3.json** is the current closed-loop target lock (2026-10-02): 38 blocks (6 constants,
   7 Data Routers), against v2's 407. The user's limit was under 40. It is built by
   `tools/build_raster_sweep_v3.js`, whose header has the full spec.
   - **Use:**
     - Search by hand with the Auto switch off; the cone lever sets the scanner cone (up = wider).
     - With the target in the cone, switch Auto on. It stops with the 1° cone on the target.
     - Switch Auto off to fly by hand again. The joystick also works during Auto, as a nudge.
   - **Hardware:**
     - the Space Scanner facing the nose
     - the RCS Controller's yaw and pitch
     - the Joystick 3D's yaw and pitch
     - a lever for the cone width
     - a Switch for Auto
     - two Axis Rotometers, mounted to read positive for stick right / stick up
   - **How it works:**
     - **Cone tracker:** W = lever × e^L, and the cone input is 1.02 − W (a Remapper).
       L steps ∓1.5% a tick while the target is or isn't seen, so the cone hugs the target at every width.
     - **Steering:** the nose moves straight at 6.6 × W deg/s, about 0.27 × its angle off the target.
       - A 60-tick Differentiator checks once a second whether the cone widened.
       - If it did, the heading turns 90°: coordinate descent.
       - A 1-tick Differentiator of the check's output makes the turn a single-tick pulse, in step with that check's decision.
       - Spreading the turn over the check, or using the previous check's decision, made the turns cascade into a spin.
     - **Rate loop (Auto only):** RCS = stick − D × (rate − steer). In manual, RCS = stick.
     - **Stop:** at 1° with the target seen, W decays to 0, so the ship stops.
   - **Tuning:** one value, `tune_damp` = −D, with D ≈ 5 / (deg/s² at full stick). Measure it by holding full yaw for 1 s in manual.
     - The steer passes through D too, so the approach speed doesn't depend on it.
     - Tested good for D × α from 1.25 to 6. Around 50, the ship buzzes but still points correctly.
   - **Results:** these are from `tools/attitude_harness.js` (8 tests in `test/engine.test.js`).
     - It locks in about 12–42 s, typically 30, at RCS from 5 to 200 deg/s² with D = 5/α.
     - Also handled: a 4× mistuned D, farther and nearer bodies, rotometer noise with 3 ticks of scanner lag, and starts up to 18° off in a 50° cone.
   - **Blueprint:** installed 2026-10-02 as "raster sweep v3 (38 blocks)" in the in-game folder "au-sim gen"
     (`cc1944f8-35fa-4a49-83fa-f7d6ef480631.bp`). It uses split I/O: 7 inputs in two rows on −z, 3 outputs on +z.
     The box is 12×8×8 (12 frame quarters), and `verify_bp.py` passes it. It has not been loaded in-game yet.
     Regenerate: `node tools/make_blueprint.js circuits/raster_sweep_v3.json --io split --box 12x8x8 --seeds 6`.
   - **Limits:**
     - It stops once the 1° cone sees the target, so the nose ends within 0.5° of the target's disk. For a big planet that is its limb, not its centre (v2 centred to 0.05°).
     - A target within about 3° of the 50° cone's edge (21.6° off) can be lost on the first move.
     - An RCS deadband ≥ 0.05 stalls it about 1.5° off.
3. **raster_sweep_v2.json** *(superseded by v3; kept for reference)* is a closed-loop target lock by cone
   probing (2026-10-02). It is built by `tools/build_raster_sweep_v2.js`, whose header has the full spec.
   - **Use:**
     - Fly by hand with a wide cone until the scanner sees the target, then press Start.
     - It centres the ship on the target with the 1° cone and raises `locked`.
     - Moving the joystick (> 0.3) hands control back, and so does losing the target for 10 s.
   - **Hardware:**
     - the Space Scanner facing the nose
     - the RCS Controller's yaw and pitch, driven by the circuit
     - the Joystick 3D's yaw and pitch, wired into the circuit (passed through to the RCS in manual)
     - a Button for Start
     - two Axis Rotometers: one upright for yaw rate, one on its side for pitch rate
   - **Method:**
     - **Probe:** hold still. Try the 1° cone, then bisect the scanner input 10 times (18 ticks per probe).
       The smallest cone that sees the target gives `f`, the angular distance to its disk, to ±0.03°.
     - **Locate:** probe at the start heading, after a yaw nudge δ, and after a pitch nudge δ
       (δ = 0.3·f, between 0.5° and 5°). Then trilaterate the centre and slew to it. If the 1° cone doesn't see it
       there, probe again from that heading.
     - **Centre:** finish with one sweep pair per axis at the 1° cone. The sweeps speed up as they go (0.3°/s up
       to 2°/s), and the centre is the midpoint of the edges, so sensor lag cancels.
   - **Other bodies:**
     - The target is any reading within 5% of the distance remembered at Start; that distance keeps tracking while
       the target is seen.
     - A farther reading, or an empty cone, means the target isn't in the cone.
     - A nearer reading hides the target. Probes count it as seen, and the final sweeps keep their last answer.
   - **Tuning:** one physical value, `tune_rcs`: the ship's deg/s² at full stick (hold full yaw for 1 s and read the
     yaw rotometer). The hold loop is `kp = 6.25 / rcs`, `kd = 4.25 / rcs`. Flip `tune_yaw_sign` or
     `tune_pitch_sign` if a rotometer reads negative for stick right or up.
   - **Tick-model lessons:**
     - A latch must be a Memory block. An OR/AND feedback loop only circulates a pulse.
     - A Memory's value and set inputs must arrive through the same number of blocks.
     - An unwired Condition True input reads 1.
   - **Results** (`tools/attitude_harness.js`, 7 tests): locks in 36–50 s, centred within 0.03–0.07°. The cases
     covered:
     - RCS from 5 to 60 deg/s²
     - `tune_rcs` off by 2× either way
     - a big close planet (6° radius)
     - farther and nearer bodies crossing the cone
     - a 50° start cone
     - rotometer noise
     - an RCS deadband (88 s)

     The earlier edge-sweep design took 50–65 s.
   - **Size:** 407 blocks: 60 constants (fixed constants are copied rather than routed) and 94 Data Routers (the game
     lets an output feed one input).
4. **three_state_cycle.json** cycles 0→1→2 every 30 sec, assuming 60 ticks/sec. *(not recovered)*

6. **planet_hop_v2.json** is the suicide-burn autopilot, rebuilt 2026-10-01. The formulas are in the header of `tools/build_planet_hop.js`.
   - **Why the old version crashed:** it switched to braking at the exact moment stopping distance equalled distance remaining, with no margin. Every block takes a tick, so the readings are about 8 ticks old when the thruster acts, and at speed that costs hundreds of metres. In the flight model it hit the surface at about 90 m/s from any start speed. A negative (signed) accelerometer reading while braking also floored the braking estimate, so it braked forever and then reversed away.
   - **Lead and standoff:** the plan uses `distance − v × 0.25 s − 50 m standoff`.
   - **Braking estimate:**
     - It is `|accelerometer|`, so either sign convention works.
     - `thrust_ratio` (forward ÷ reverse) is applied only while accelerating.
     - The value is held in a Memory that only updates after 10 ticks of steady full thrust.
     - The plan uses 95% of it, plus gravity (+ helps braking, − hurts).
   - **Committed, throttled burn:**
     - Once braking starts with a known estimate, it stays committed until enable is cycled.
     - The throttle is `stop ÷ d_plan` (about 0.95 on the curve), with a minimum of 0.5 so the last metres don't taper off forever.
     - This removes the accelerate/brake chatter that crashed ships with uneven forward and reverse thrust.
   - **Already moving at enable:**
     - The estimate is unknown at that point, because the accelerometer reads 0 while coasting.
     - The circuit brakes at full thrust until it has measured the estimate, then replans. That may mean accelerating again if the target is still far.
     - It never commits on a stale decision: commitment waits 10 ticks after the estimate becomes known.
   - **Stop and shutdown:**
     - `stopped = enable AND (stopped OR (braking AND v ≤ (|accelerometer| + gravity) × 0.15 s))`, a logic hold.
     - Thrust is then 0 until enable is switched off and on again, so the ship never reverses away.
     - The **arrived** Datameter outputs it. Under gravity the ship falls once thrust is cut, so hand over to hover/landing on `arrived`.
   - **Constants:**
     - Removed: `const_zero`, `const_fallback_one`, `const_decision_true` and `const_pow_two`, because unwired Condition ports default to B = 0, True = 1 and False = 0. v² is v × v, and the ×2 is folded into the 1.9 margin.
     - What's left is tuning only: lead 0.25 s, standoff 50 m, cut 0.15 s, margin 1.9, minimum brake 0.5, and two ÷0 floors.
     - A test checks that no constant repeats a Condition default.
   - **Flight-model results:**
     - The model covers: from rest, already moving (300–2,000 m/s), enabled mid-coast, both accelerometer conventions, a signed velocity meter, a 2:1 thrust ratio, an unknown ratio, gravity 5 and 15 m/s² against 20 m/s² of thrust, weak thrust over 1,000 km, and a 2 km hop.
     - Every case stops 50–67 m out at under 0.7 m/s, with thrusters off.
   - **Inputs:** distance, velocity, accelerometer, thrust_ratio (0 = assume 1), gravity and enable.
   - **Outputs:** `thruster_out` (−1..1, where a negative value needs a reverse thruster or a Sign Splitter), `time_to_arrival` and `arrived`.
   - **Blueprint:** installed 2026-10-02 as "planet hop v2 (24 fq, black, I/O row)" in the in-game folder "au-sim gen"
     (`a02806e7-a47b-45d8-9606-e8ac73888bb6.bp`). It is 8×8×24, with all 9 I/O in one three-row bundle on −z.
     It replaces the 24-quarter "planet hop v2 (24 fq, labels)" (`9927cd90`), which used the old colours.

7. **planet_hop_flip.json** is the flip-and-burn autopilot (2026-10-03): a modified planet_hop that burns nose first, turns
   around automatically with maneuvering thrusters at the last safe moment (the turn's coast planned in) and burns the
   same engines to stop. 80 blocks, no constants. Formulas in the header of `tools/build_planet_hop_flip.js`.
   - **Sensors (radio, SHIP RADIOS channels):** 30 FWD DIST (Space Scanner on the nose), 38 REAR DIST (Long Range
     Distance Meter on the tail), 23 Z SPEED (Velocity Meter, Directional, facing forward). Local: Accelerometer,
     Gravitymeter, two Axis Rotometers (yaw, pitch), the Autopilot switch, the pilot's Joystick 3D.
   - **Outputs:** 1 THRUST CTL, 10/11 ROLL±, 12/13 YAW±, 14/15 PIT±, and 31 SCAN ANGLE from a knob. The joystick adds
     into the yaw and pitch commands and drives roll, so this circuit is the one sender on all six attitude channels.
     With the Autopilot off the holds send nothing and the stick flies the ship on the maneuvering thrusters.
   - **Plan:** the burn runs only while the scanner sees a target. The flip commits once the forward speed passes
     v_prof = √(1.9 · (a_held − g) · d_plan) − fade_w, with d_plan = distance − standoff − v · lead (lead 16 s covers
     the ~11 s turn and the delays); the commit must hold for 20 ticks, so a half-measured acceleration at a mid-flight
     start cannot trigger it.
   - **Turn:** rate command min(√(2 · 3°/s² · degrees left), 2/s · degrees left) on |θ|, so it is sign-free and pulls
     back an overshoot. Braking thrust ramps in from 170° turned.
   - **Braking and hover:** thrust = sat(−(vf + v_prof) ÷ 120 m/s) + g ÷ a_held, on the signed forward speed. Once the
     profile reaches zero this hovers the ship tail down; it never backs away. The tail meter's distance is used once it
     sees the target; while it sees nothing (mid-turn, or a tail a few degrees off a far target) the distance counts as 0,
     "brake now", so the ship stops short and hovers rather than coasting in blind.
   - **Holds:** the engines push slightly off the centre of mass (on a 56 t test ship, 0.22 quarters: 5.8°/s² of pitch
     at full electric thrust), so pitch, and yaw until the flip, are held at the Autopilot-on attitude by PD loops on the
     integrated rotometer rates. Unlike the turn these depend on the rotometer signs: on a first flight, check that the
     yaw rotometer reads + for nose right and the pitch one + for nose up, and turn one over if not.
   - **Lessons:**
     - Unsigned speed (A SPEED) cannot tell stopped-and-backing-away from approaching, which is why v2 needed a stopped
       latch. A Directional Velocity Meter gives the sign for free.
     - Thrusters slew (1 / acceleration_time per second): fuel engines take 10–20 s, so autopilots drive electrics only.
     - A latch must not be reset by a signal with unequal path lengths: REAR DIST × validity passed one tick of 1e20 when
       the tail lost the target, which dropped the target lock and cancelled the flip mid-braking. The latch now resets
       only from the Autopilot switch.
     - A fade band on a speed profile eats the braking margin unless the profile is shifted down by the band.
   - **Flight-model results** (`node tools/flip_harness.js`, 71 cases: 50 km to 5,000 km, 40–220 m/s², gravity 0–9.8,
     yaw authority 5–20°/s², both RCS and rotometer signs for the turn, thrust lag 0.05–0.5 s, aim off 2–8°, a 3 km/s
     start, a 20 km hop, and a 56 t test ship's numbers with its mass model's thrust offsets and twice them): 66 end
     hovering tail down 99–188 m above the surface (by the tail meter) or stopped in free space, with the holds keeping
     the nose within 1.4° (2.8° at twice the offsets). The other 5 pair half the test ship's turning authority with twice
     its offsets, so the offset torque nears what the thrusters can answer: the nose swings 40–57° and three of them miss.

## Reusable physics

- **Symmetric trip** (accelerate, flip, decelerate, at rest at both ends): `D/2 = ½·a·(T/2)²`
- **Thrust-to-weight:** `T/W = a / 9.81`. This uses standard gravity and does not depend on mass.
- **Turnaround speed** over distance D: `v = √(a·D)`
- **Dropping mass:** this lowers the thrust force needed but does not change T/W, unless the turnaround point is also moved later.
- **Accelerometers** read |dv/dt| (game code): gravity is included, so during a burn toward a planet the reading is thrust + g. planet_hop_flip subtracts g before holding the reading and subtracts g again for braking.

## Subsystem designs (flight-computer.html)

- **Hover:** altitude-hold plus horizontal-drift cancel, using a PD loop off the Altimeter and Velocity Meter.
- **Level flight:** Gyro-Line → `÷ −30` → summed with the joystick, plus a differentiator damping term.
- **Obstacle avoidance:** a reactive rangefinder flinch. This is the weakest-evidenced subsystem, because no confirmed proximity sensor exists.
- **Autopilot cruise:** Space GPS + heading calc + braking. The braking part is superseded by planet_hop_v2.
- **Planet scan:** raster sweep + rangefinder lock + a min/max distance band-pass filter.

## Blueprint generation (in progress, 2026-10-02)
- **Goal:** a "Download blueprint" button that packs a simulator circuit into an in-game `.bp`. It includes only parts the size of a Data Router 4 or smaller, densely packed. Larger parts are replaced by a cable to the blueprint's edge plus a label.
- **Format:** `tools/bp/` has the decoded format (`NOTES.md`), a verified reader/writer (`bpformat.py`) and load tests (`make_load_tests.py`).
- **Frames, glass and welding** (2026-10-02): `tools/bp/parts/structure_meshes.md` covers shapes, welds, masses and joint strength. `tools/bp/extract_structure.py` extracts the meshes (`tools/bp/meshes/*.obj`) and properties (`parts/structure_meshes.json`). From the user:
  - A weld covers a whole face. It makes the part stronger and heavier; every face welded = 2× mass.
  - Interior faces are unconnected faces facing the ship's inside; exterior faces are unconnected faces on the outside.
  - A partly covered face still needs welding. One side can be two coplanar faces, each welded separately.
  - "Curved" parts are angular, with 1:1 (45°) and 1:2 (26.6°, "30°") slopes.
- **Frame rotation model:** `tools/bp/parts/orientation_check.py` confirmed it against the corpus: slopes rest against another part 0.4% of the time, flat faces 78% (6% and 53% for the inverse rotation).
- **Reference blueprint:** `rosetta.json` is the spec for the "rosetta" reference blueprint the user built in-game. It maps part hashes to part names.
  - The user removed "rosetta", "rosetta M" and "mirror test" from the game on 2026-10-02. Copies are in `tools/bp/reference/`, where `decode_rosetta.py` and `corpus.py` look for them.
- **User's blueprints:** `%USERPROFILE%\AppData\LocalLow\ApproximatelyGames\ApproximatelyUp\Blueprints` (plus `BlueprintsBin`, which the game writes to on launch).
- **Generator:** `bpgen.js`, with CLI `tools/make_blueprint.js` and the Blueprint button in the simulator. `tools/bp/GENERATOR_SPEC.md` has the details. The user's style rules (2026-10-02):
  - Logic parts and internal cables are black; only the I/O is colour-coded (inputs green, outputs red, labels to match).
  - The I/O comes out as a group of parallel cables where possible: one row ("bundle"), else inputs and outputs in a row each ("split").
  - The CLI searches box × I/O mode × seed on all CPUs, because one try at a 40-part circuit rarely succeeds.
  - **Flat** (2026-10-03, `--flat` / the simulator's Flat box): every logic part rests on a floor of Frame Quarters
    that holds it (top up, or on a side where that helps); wires use the fewest of up to four levels, routed like a
    multi-layer circuit board with the parts on its bottom layer; each label lies beside its end. `--no-floor` leaves
    the floor out, for pasting onto a floor of your own. Details and timings in GENERATOR_SPEC.md.

## Open gaps

- **Logic gate truthiness is unconfirmed.** The engine treats non-zero as true; the game may use >= 0.5.
- **Division by zero:** the game's behaviour for `/0`, `mod 0` and `log <= 0` is unknown. The engine returns 0.
- **Unconfirmed sensor behaviour:**
  - The Gyro-Line sign conventions
  - Whether Data Redirector 3 picks the nearest setpoint or uses thresholds
- **The `adder` type_id on aupbuilder is still unverified,** as are the new type ids listed above.
- **Power figures:** P/s draws, generation and battery capacities are placeholders until copied from the in-game tooltips. Decoding them from the asset files would need Il2CppDumper-generated type trees.
- **planet_hop is only tested in a 1-D model.** It assumes thrust acts along the line to the target, the accelerometer reads thrust only, and the ship doesn't need to rotate to brake (a reverse thruster or Sign Splitter). A ship that has to turn around should use planet_hop_flip, which plans the turn in.
- **planet_hop_flip is tested in a 1-D model with yaw** (`tools/flip_harness.js`): straight-line approach to the target's centre, no lateral drift, the target fixed in space. Orbiting targets, off-axis aim beyond the scanner cone and the real RCS/rotometer signs are untested in the game.
- **Approximated behaviours:**
  - The BPS and ETA indicator formulas, which are built from stopping distance v²/2a against distance left
  - The demand modes above
  - What happens on a circuit that is short of power. The model blacks out the whole circuit; the game may brown out partially.
  - Plasma and video, which carry only a level or a live/dead flag
- **Not modelled:** fuel, heat, the 150 P/s cable burn, Frame Quarter With Ports chains, and physics.
